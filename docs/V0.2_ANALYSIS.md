# v0.2 Analysis Foundation

## Purpose

v0.2 adds a read-only mailbox analysis layer behind the existing v0.1 mutation boundary.

The analysis system answers:

> What evidence do we have about the messages in this query, and which messages match an explicit review rule?

It does **not** answer:

> Which messages should be deleted?

That decision remains with the operator.

## Runtime boundary

```text
Gmail API
   |
   v
lightweight message metadata
   |
   v
normalization
   |
   v
analysis core
   |
   +--> sender distribution
   +--> category distribution
   +--> age distribution
   +--> explicit review candidates
   |
   v
structured report
   |
   v
operator decision
   |
   v
existing v0.1 safety gate
   |
   v
TRASH-only mutation
   |
   v
verification
```

The analysis core must never call `batchModify` or any permanent-delete endpoint.

## Message observation model

The normalized internal record contains only data needed for analysis:

- message ID
- thread ID
- normalized sender name
- normalized sender email
- subject
- internal timestamp
- Gmail label IDs

Bodies, attachments, snippets, raw MIME content, and exported mailbox data are outside the v0.2 analysis scope.

## Deterministic analysis

The analysis core exposes pure, testable functions for:

1. Sender normalization.
2. Gmail category extraction from known category labels.
3. Age bucketing relative to an explicit `now` value.
4. Sender/category/age distributions.
5. Explicit review candidates.

The analysis result is structured data so CLI renderers can produce human-readable output and machine-readable formats without changing the analysis logic.

## Candidate rule

The initial candidate rule is deliberately transparent:

`review candidate = message is in an operator-selected category AND is at least N days old`

A candidate is a **review signal**, not an instruction to mutate anything.

Each candidate contains enough metadata for an operator to inspect the signal without another message fetch:

- message ID
- sender email
- subject
- integer age in days
- known Gmail categories
- explicit reason strings such as `category:promotions` and `age:180d+`

The report contains no opaque score or classifier. Candidate reason values are deduplicated and emitted in stable order.

## Privacy boundary

The analysis layer should request the smallest Gmail representation that satisfies the report.

The first integration uses Gmail `format=metadata` with only required headers (`Subject` and `From`) plus message labels/timestamps. It does not download bodies or attachments.

## Failure behavior

Analysis should fail loudly on malformed records rather than silently inventing values.

Network/API error handling belongs at the Gmail adapter boundary. The pure analysis layer remains deterministic and free of network calls.

## Validation status

The v0.2 read-only analysis path has been validated on a real Android/Termux environment using Python 3.14.6. The merged foundation passed 43/43 local tests, and the candidate-reporting refinement passed 44/44 local tests. The deterministic candidate proof produced exactly one expected candidate, and real Gmail `--analyze` runs returned valid structured JSON without mutations. The post-merge `main` checkout was verified on Termux at merge commit `ce46fdf0e9dd5f89f41ca1fe4a5446261114bc8c`.

GitHub Actions test and security workflows both passed for the merged commit. No Gmail mutation was performed during v0.2 analysis validation.

The v0.2 analysis scope is therefore complete for this release candidate. The next work should focus on release packaging and later reporting/verification improvements rather than automated deletion intelligence.

## Implementation order

1. Land the pure analysis data model and tests.
2. Add a Gmail metadata adapter.
3. Add a read-only analysis command.
4. Add structured output.
5. Perform read-only real-device validation.
6. Refine candidate/report ergonomics.
7. Only then consider richer reporting or reusable analysis presets.
