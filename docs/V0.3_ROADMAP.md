# v0.3 Roadmap — Evidence-first cleanup workflow

## Purpose

v0.2.0 established the read-only analysis foundation:

`observe → normalize → analyze → report → operator decision → existing safety gate → apply → verify`

v0.3 should make that workflow substantially better for real operators without introducing automatic deletion intelligence.

The central rule remains:

> **The tool may explain evidence and execute an explicitly approved Trash action; it must not silently decide what to delete.**

## v0.3 scope

### 1. Safer verification and batch reporting

**Status: implemented and merged.**

Issue: #13

The mutation path currently reports whether batches succeed, but v0.3 should make the result a first-class verification record.

Target behavior:

```text
search
  ↓
preview
  ↓
explicit approval
  ↓
batch Trash operation
  ↓
bounded verification
  ↓
final report
```

The verification layer should:

- report successful and failed batches separately
- retain the IDs needed to explain partial completion
- verify that successfully processed messages have the expected Trash state
- distinguish `verified`, `not-verified`, and `verification-error`
- remain read-only during verification
- fail closed when verification data is ambiguous

No verification feature should introduce a second mutation path.

### 2. Operator-facing reports and machine-readable output

**Status: implemented and merged.**

Issue: #15

Separate report construction from Gmail networking and mutation so the same evidence can be rendered in different forms.

The shipped report model has explicit schema metadata.

Analysis reports currently expose:

```text
schema_version
report_type
query
matched
analysis
```

Cleanup reports additionally expose:

```text
mutation
verification
```

Human output should answer, quickly:

- What did I ask the tool to inspect?
- What did it find?
- What does it recommend for review?
- Did anything change?
- Was the requested change verified?

JSON output should remain deterministic enough for shell scripts and downstream tooling.

Bodies, attachments, raw MIME content, and opaque classifier scores remain outside the report model.

### 3. Reusable cleanup presets

**Status: implemented and merged.**

Issue: #14

Operators should be able to save a reviewed cleanup recipe instead of repeatedly typing long command lines.

Example concept:

```text
preset: old-promotions

query = category:promotions older_than:1y
max_results = 100
preview = 25
candidate_category = promotions
candidate_older_than = 180
```

Requirements:

- local and human-readable configuration
- no OAuth credentials or access tokens in presets
- explicit validation of every field
- deterministic precedence when CLI flags override preset values
- `--apply` and confirmation rules remain unchanged
- invalid presets fail closed

The project should not add cloud-synced or remotely executable presets in v0.3.

### 4. Portability and configuration-path improvements

**Status: implemented and merged.**

Issue: #16

Keep Android/Termux as the primary environment while reducing hard-coded path assumptions.

Target outcomes:

- one central path-resolution implementation
- clean `GMAIL_CREDENTIALS` / `GMAIL_TOKEN` handling
- predictable user config locations where supported
- tests for path precedence and platform differences
- documentation that distinguishes supported behavior from incidental behavior

The Gmail API scope and credential privacy boundary must not change.

## Safety invariants

Every v0.3 feature must preserve these properties:

1. Dry run is still the default.
2. Mutation still requires `--apply`.
3. Interactive mutation still requires the exact confirmation word `TRASH`.
4. Non-interactive mutation remains an explicit opt-in.
5. Broad-query protection remains enforced.
6. Permanent deletion remains unsupported.
7. Analysis remains metadata-only.
8. Verification never becomes a mutation mechanism.
9. No opaque classifier is allowed to approve Trash actions.
10. Presets cannot bypass the existing safety gate.

## Intended end-to-end flow

```text
CLI + optional preset
        ↓
argument/config validation
        ↓
Gmail search
        ↓
metadata observation
        ↓
normalization
        ↓
analysis
        ↓
human + JSON report
        ↓
operator review
        ↓
existing safety gate
        ↓
TRASH mutation
        ↓
bounded verification
        ↓
final report
```

## Implementation order

### Phase A — reporting foundation — complete

1. Define report data structures and schema version.
2. Add pure renderers.
3. Extend tests without contacting Gmail.
4. Preserve the existing v0.2 JSON compatibility where practical.

### Phase B — mutation verification — complete

1. Refactor mutation results into explicit batch outcomes.
2. Add bounded Trash verification.
3. Add partial-failure and mismatch tests.
4. Integrate verification into the operator report.

### Phase C — presets — complete

1. Choose a small local configuration format.
2. Implement strict parsing and validation.
3. Add preset listing, showing, and preset-backed execution.
4. Test CLI/preset precedence.
5. Confirm presets cannot bypass safety checks.

### Phase D — portability — complete

1. Centralize path resolution.
2. Add platform-aware tests.
3. Update authentication documentation.
4. Re-run the complete suite on Termux.

## Release validation bar

Do not call v0.3 complete until all of the following are observed:

- [x] Full unit suite passes in GitHub Actions after each v0.3 implementation slice.
- [x] Ruff checks pass in GitHub Actions.
- [x] Dependency/security workflow passes.
- [ ] Real Android/Termux installation works with the complete v0.3 implementation.
- [ ] Real Gmail read-only analysis works with the complete v0.3 implementation.
- [ ] At least one controlled reversible Trash mutation is performed with the v0.3 implementation.
- [ ] Post-mutation verification produces the expected result on real Termux/Gmail.
- [x] Partial-failure behavior is covered by deterministic tests.
- [ ] Presets are validated on the real target environment.
- [ ] Documentation and changelog match the final shipped behavior.
- [ ] v0.3.0 is published from `main`.

## Explicitly out of scope

- Permanent Gmail deletion.
- Automatic deletion or archival based on AI/ML inference.
- Reading message bodies solely to improve cleanup decisions.
- Attachment inspection/export.
- Cloud-synced presets.
- Scheduled background deletion.
- Credential storage in preset files.
- A broader platform expansion that weakens focus on Android/Termux.

## Learning objective

v0.3 is not just a feature release. It should deepen the engineering lessons already exercised by the project:

- API boundary design
- deterministic data models
- CLI UX
- configuration precedence
- failure handling
- verification
- testing strategy
- release engineering
- portability
- security-conscious automation
