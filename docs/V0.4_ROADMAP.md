# v0.4 Roadmap — Reviewable cleanup plans

## Purpose

v0.3 made the cleanup workflow observable, reportable, verifiable, and reusable. v0.4 adds one more explicit boundary: a cleanup operation can be represented as a local plan that the operator can inspect before execution.

Target workflow:

`observe → analyze → generate plan → review plan → explicit apply → verify`

A plan is **not** an autonomous decision. It is an explicit record of what an operator has already chosen to execute.

## v0.4 goals

- Separate planning from execution.
- Make the exact execution target inspectable before Gmail is mutated.
- Detect stale or altered plans before they can be applied.
- Keep plans local, deterministic, metadata-only, and credential-free.
- Preserve every v0.3 safety invariant.

## Proposed plan schema

Use a versioned JSON document:

```json
{
  "schema_version": "0.4",
  "plan_type": "gmail_cleanup",
  "created_at": "…",
  "query": "category:promotions older_than:1y",
  "operation": "trash",
  "message_ids": ["…"],
  "matched": 10,
  "analysis": {
    "candidate_count": 3
  },
  "safety": {
    "apply_required": true,
    "permanent_delete": false
  },
  "source_fingerprint": "…"
}
```

### Required fields

- `schema_version`: plan format version.
- `plan_type`: identifies the plan family.
- `query`: exact Gmail query used to select the messages.
- `operation`: currently only `trash`.
- `message_ids`: explicit message IDs to operate on.
- `matched`: number of IDs captured in the plan.
- `safety`: explicit invariant state.
- `source_fingerprint`: deterministic fingerprint over the relevant plan inputs.

### Optional fields

- `created_at`: informational creation timestamp.
- `analysis`: evidence that helped the operator decide.
- future report linkage fields.

## Fingerprinting and staleness

The plan must not blindly trust a file just because its JSON is valid.

The execution layer should compute the same deterministic fingerprint from the plan's canonical fields and compare it with `source_fingerprint` before mutation.

A mismatch must fail closed.

Potential future hardening:

- bind a plan to the account identity without writing private credentials into the plan
- optionally re-check that the listed IDs still satisfy the original query
- reject plans whose operation is unsupported by the current CLI

These checks should be added only when their semantics are deterministic and testable.

## Safety boundary

Plan execution must call the **same** mutation gate used by normal CLI execution.

Required invariants:

1. A plan cannot mutate Gmail without explicit `--apply`.
2. Interactive execution still requires exact `TRASH` confirmation.
3. Non-interactive execution remains explicit.
4. Broad-query protection remains authoritative.
5. The plan cannot request permanent deletion.
6. Plans contain no OAuth credentials, access tokens, message bodies, or attachments.
7. Verification remains read-only.
8. A malformed, stale, unsupported, or mismatched plan fails closed.

## CLI concept

Initial interface proposal:

```text
gmail-cleaner --query '…' --plan-out cleanup-plan.json
gmail-cleaner --plan-show cleanup-plan.json
gmail-cleaner --plan-apply cleanup-plan.json --apply
```

Exact option names are not final until the runtime design and tests are written.

Generating a plan must not mutate Gmail.

Showing a plan must not mutate Gmail.

Applying a plan must still pass the existing safety gate.

## Implementation phases

### Phase A — pure plan model

- Define immutable plan data structures.
- Define canonical serialization.
- Define deterministic fingerprinting.
- Add strict validation.
- Add malformed/stale fixture tests.

### Phase B — plan generation

- Add plan output from an existing query/analysis result.
- Keep generation read-only.
- Add human-readable plan inspection.

### Phase C — plan execution

- Add plan input validation.
- Reuse the existing mutation gate.
- Execute exactly the IDs in the reviewed plan.
- Produce the existing cleanup + verification report with plan linkage.

### Phase D — real-device validation

- Generate a plan on Termux.
- Inspect it.
- Validate read-only behavior.
- Apply one disposable plan.
- Confirm verification.
- Test stale-plan rejection without mutation.

## Explicit non-goals

- AI-generated deletion decisions.
- Scheduled cleanup.
- Cloud-synced plans.
- Permanent deletion.
- Automatic plan approval.
- Hidden background mutation.

## Release bar

Do not release v0.4 until:

- [ ] Plan schema is documented and versioned.
- [ ] Canonical serialization is deterministic.
- [ ] Fingerprint mismatch fails closed.
- [ ] Plan generation is proven read-only.
- [ ] Plan execution preserves all v0.3 safety gates.
- [ ] Unit tests cover valid, malformed, altered, stale, and empty plans.
- [ ] Real Android/Termux validation passes.
- [ ] Real Gmail validation includes one controlled reversible plan execution.
- [ ] Documentation/changelog match shipped behavior.
- [ ] GitHub Release v0.4.0 is published from `main`.

## Learning objectives

v0.4 should deepen the engineering lessons from v0.3:

- data contracts and schema evolution
- canonical serialization
- hashing/fingerprinting
- state validation
- transactional thinking
- CLI interface design
- safe replay of explicit user intent
- deterministic testing
- security-conscious local artifacts
